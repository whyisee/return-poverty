# 中年返贫四件套经营模拟器开发设计文档

> 版本：v0.1  
> 日期：2026-05-13  
> 关联方案：`docs/中年返贫四件套经营模拟器设计方案.md`  
> 技术栈：React + Vite + Ant Design / Python / MySQL

## 1. 文档目标

本文档用于把《中年返贫四件套：小店生死账》的方案设计落到前后端开发实现层面，明确：

- 前端项目如何组织页面、组件、状态和交互。
- 后端项目如何提供模拟引擎、存档、结算和内容配置能力。
- MySQL 如何承载用户局、事件卡、决策卡、账本、结局报告等核心数据。
- MVP 阶段优先实现哪些接口和页面，后续如何扩展完整流程版。

本项目第一阶段建议做成前后端分离 Web 应用：

- 前端负责沉浸式经营体验、决策交互、账本展示和报告呈现。
- 后端负责游戏局状态、规则计算、事件抽取、账本结算、存档和内容配置。
- MySQL 负责持久化模拟配置、用户存档、经营流水和结局报告。

## 2. 技术选型

### 2.1 前端

| 项目 | 选型 | 说明 |
| --- | --- | --- |
| 框架 | React | 组件化承载章节式经营流程 |
| 构建工具 | Vite | 启动快，适合独立前端项目 |
| UI 组件 | Ant Design | 表单、卡片、步骤条、统计数值、表格、弹窗成熟 |
| 路由 | React Router | 首页、经营台、账本、报告等页面切换 |
| 请求 | Axios 或 Fetch 封装 | 统一处理 API 地址、错误、登录态 |
| 状态 | Zustand 或 React Context | 保存当前游戏局、章节状态、指标面板 |
| 图表 | ECharts 或 Ant Design Charts | 展示现金流趋势、成本结构、风险来源 |
| 语言 | TypeScript 推荐 | 模拟状态和接口数据较复杂，类型能降低错误 |

### 2.2 后端

| 项目 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | Python | 满足需求，适合快速实现规则引擎和 API |
| Web 框架 | FastAPI 推荐 | 原生 OpenAPI、Pydantic 校验、异步能力好 |
| ORM | SQLAlchemy 2.x | MySQL 兼容成熟，便于模型管理 |
| 迁移 | Alembic | 维护数据库表结构版本 |
| 配置 | Pydantic Settings | 管理数据库、跨域、环境变量 |
| 测试 | Pytest | 覆盖规则计算、接口和账本公式 |
| 日志 | logging / structlog | 记录模拟结算、异常和关键行为 |

如果团队更熟 Flask，也可以采用 Flask + SQLAlchemy；本文档以下按 FastAPI 描述。

### 2.3 数据库

| 项目 | 选型 | 说明 |
| --- | --- | --- |
| 数据库 | MySQL 8.x | 存储游戏配置、存档、账本和报告 |
| 字符集 | utf8mb4 | 支持中文文案和分享内容 |
| JSON 字段 | MySQL JSON | 存储灵活的规则效果、快照和报告详情 |
| 主键 | BIGINT 自增或 CHAR(36) UUID | 配置表可自增，游戏局可 UUID |

## 3. 总体架构

```text
Browser
  |
  | HTTP JSON
  v
React + Vite + Ant Design
  |
  | /api/v1
  v
Python FastAPI
  |-- Game Service        游戏局生命周期
  |-- Simulation Engine   客流、账本、风险、结局计算
  |-- Content Service     角色、赛道、事件卡、决策卡
  |-- Report Service      创业体检报告
  v
MySQL
```

核心原则：

- 规则计算放在后端，避免前端篡改或多端结果不一致。
- 前端保留必要的当前局缓存，用于页面切换和弱网体验。
- 内容卡片配置入库，后续可以不发版调整事件、决策和文案。
- 每次关键决策都记录快照，便于复盘、恢复和生成结局报告。

## 5. 核心业务流程

### 5.1 快速体验版

```text
进入首页
  -> 选择快速体验
  -> 选择角色
  -> 选择赛道
  -> 选择开局包
  -> 创建游戏局
  -> 第 1-7 天循环：
       拉取当天事件和可选决策
       玩家选择 2-3 张决策卡
       后端结算当天账本
       前端展示现金流和家庭压力变化
  -> 生成快速体检报告
```

### 5.2 完整流程版

```text
进入首页
  -> 选择完整流程
  -> 角色与家庭底线
  -> 入局评估
  -> 赛道选择
  -> 筹备开店
  -> 开业冲刺
  -> 稳定经营
  -> 危机与诱惑
  -> 创业体检报告
```

完整流程版使用章节状态机控制：

| phase | 名称 | 前端页面 | 结算单位 |
| --- | --- | --- | --- |
| motivation | 动心 | RoleSetupPage | 一次性 |
| precheck | 入局评估 | RoleSetupPage / PreparationPage | 一次性 |
| track_select | 选赛道 | TrackSelectPage | 一次性 |
| preparation | 筹备开店 | PreparationPage | 一次性 |
| opening | 开业冲刺 | OperationDeskPage | 日 |
| stable | 稳定经营 | OperationDeskPage | 周 |
| crisis | 危机与诱惑 | CrisisPage | 事件回合 |
| report | 结局复盘 | ReportPage | 一次性 |

## 6. 前端开发设计

### 6.1 页面设计

#### 首页 HomePage

职责：

- 展示项目名称和两个入口：完整流程、快速体验。
- 展示继续上次游戏入口。
- 展示四个赛道的轻量入口。

AntD 组件建议：

- `Button`
- `Card`
- `Row` / `Col`
- `Statistic`
- `Modal`

#### 角色与家庭底线 RoleSetupPage

职责：

- 选择玩家角色。
- 设置或确认初始现金、家庭支出、债务、体力、压力。
- 展示“可承受亏损月数”。

关键交互：

- 切换角色时刷新默认参数。
- 用户可在允许范围内调整家庭支出和可用资金。
- 点击确认后调用创建游戏局接口。

#### 赛道选择 TrackSelectPage

职责：

- 选择奶茶、汉堡、咖啡、烘焙。
- 展示客单价、表面毛利、最大风险、独有系统。
- 将选择写入当前游戏局。

#### 筹备开店 PreparationPage

职责：

- 选择加盟/自营、位置、面积、装修、设备、首批物料、员工数。
- 实时展示启动资金表、剩余流动资金和可撑天数。
- 提交筹备决策后进入开业冲刺。

#### 经营台 OperationDeskPage

职责：

- 承载开业冲刺和稳定经营的主循环。
- 左侧展示核心指标：现金、债务、可撑天数、家庭压力、体力、口碑、复购。
- 中间展示营业过程、事件反馈和订单摘要。
- 右侧展示可选决策卡。
- 底部展示账本摘要和风险提示。

核心组件：

- `MetricBar`
- `PhaseStepper`
- `EventPanel`
- `DecisionCard`
- `LedgerTable`
- `RiskAlert`

#### 账本页 LedgerPage

职责：

- 展示日账本、周账本、累计账本。
- 拆分营业额、原料、人工、房租、平台抽成、满减、营销、损耗。
- 用图表展示现金流趋势和成本占比。

#### 危机页 CrisisPage

职责：

- 展示危机或诱惑事件。
- 给出追加投流、借款、砍 SKU、转让止损等选择。
- 强化“止损也是高分结局”的反馈。

#### 报告页 ReportPage

职责：

- 展示创业体检报告。
- 展示结局类型、总流水、净现金流、最大亏损来源、做对的决策、危险决策。
- 生成分享文案。

### 6.3 前端请求封装

统一封装 `frontend/src/services/http.ts`：

```ts
import axios from 'axios';

export const http = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '/api/v1',
  timeout: 10000,
});

http.interceptors.response.use(
  response => response.data,
  error => {
    const message = error.response?.data?.message || '请求失败，请稍后重试';
    return Promise.reject(new Error(message));
  },
);
```

### 6.4 交互原则

- 所有关键决策提交前给出成本和风险提示。
- 结算后必须展示“流水”和“净现金流”的差异。
- 当现金可撑天数低于阈值时，用 `Alert` 明确提示。
- 不使用单一总分掩盖成本结构，报告必须拆解亏损来源。
- 快速体验版不要求登录；完整流程版第一版也可用匿名会话。

## 7. 后端开发设计

### 7.1 API 分层

```text
api layer
  接收请求、参数校验、返回 JSON

service layer
  编排业务流程，例如创建游戏局、执行决策、生成报告

engine layer
  纯规则计算，例如客流、账本、风险、结局判断

repository layer
  数据库读写
```

### 7.2 核心服务

#### ContentService

职责：

- 查询角色、赛道、事件卡、决策卡、结局配置。
- 按版本加载内容配置。
- 后续支持后台维护和灰度版本。

#### SessionService

职责：

- 创建游戏局。
- 保存当前状态快照。
- 查询最近游戏局。
- 标记游戏局完成或放弃。

#### SimulationService

职责：

- 根据当前局、事件和决策执行结算。
- 更新现金、债务、压力、体力、口碑、复购等指标。
- 生成日账本或周账本。

#### ReportService

职责：

- 根据完整账本和决策轨迹生成结局报告。
- 判断结局类型。
- 生成分享文案。

### 7.3 规则引擎模块

```text
engine/
  traffic.py       计算客流、转化率、客单价
  ledger.py        计算营业额、成本、净现金流
  risk.py          计算可撑天数、风险等级、家庭压力
  event_picker.py  根据阶段和 flags 抽取事件
  ending.py        判断结局类型
  formulas.py      存放通用公式和边界处理
```

规则引擎应尽量写成纯函数，便于测试：

```python
def calculate_ledger(session_state, decisions, event):
    """Return ledger result without writing database."""
    ...
```

### 7.4 后端异常规范

统一返回：

```json
{
  "code": "SESSION_NOT_FOUND",
  "message": "游戏局不存在",
  "details": {}
}
```

常见错误码：

| code | 场景 |
| --- | --- |
| SESSION_NOT_FOUND | 游戏局不存在 |
| INVALID_PHASE | 当前阶段不能执行该操作 |
| DECISION_NOT_ALLOWED | 决策卡不适用于当前局 |
| CONTENT_VERSION_MISSING | 内容配置版本不存在 |
| REPORT_ALREADY_EXISTS | 结局报告已生成 |

## 9. MySQL 数据库设计

### 9.1 命名约定

- 表名使用小写蛇形：`game_sessions`。
- 时间字段统一使用 `created_at`、`updated_at`。
- 软删除字段使用 `deleted_at`，MVP 可暂不启用。
- 金额统一用“分”存储，避免浮点误差；前端展示时转换为元。
- 比例使用基点或小数。推荐 MySQL `DECIMAL(10,4)`。

### 9.2 表结构概览

| 表 | 用途 |
| --- | --- |
| content_versions | 内容配置版本 |
| roles | 玩家角色配置 |
| business_tracks | 四件套赛道配置 |
| event_cards | 事件卡 |
| decision_cards | 决策卡 |
| ending_rules | 结局规则 |
| game_sessions | 游戏局主表 |
| session_snapshots | 游戏局状态快照 |
| session_decisions | 玩家决策记录 |
| ledger_entries | 日/周账本 |
| reports | 结局报告 |

### 9.3 配置表

#### content_versions

```sql
CREATE TABLE content_versions (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  version_code VARCHAR(64) NOT NULL UNIQUE,
  name VARCHAR(128) NOT NULL,
  status VARCHAR(32) NOT NULL DEFAULT 'draft',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

#### roles

```sql
CREATE TABLE roles (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  content_version_id BIGINT NOT NULL,
  role_key VARCHAR(64) NOT NULL,
  name VARCHAR(128) NOT NULL,
  description TEXT,
  initial_metrics JSON NOT NULL,
  advantages JSON,
  risks JSON,
  sort_order INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_roles_version_key (content_version_id, role_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 10. 核心计算设计

### 10.1 客流计算

```text
客流 = 基础客流
  × 位置系数
  × 天气系数
  × 口碑系数
  × 营销系数
  × 竞争系数
  × 阶段热度系数
```

建议后端返回每次结算的拆解，前端可以展示“为什么今天客流变了”。

### 10.2 账本计算

```text
营业额 = 客流 × 转化率 × 客单价

原料成本 = 营业额 × 原料成本率
平台抽成 = 外卖营业额 × 平台抽成率
满减优惠 = 营业额 × 优惠率
报废损耗 = 备货金额 × 报废率

经营净现金流 =
  营业额
  - 原料成本
  - 平台抽成
  - 满减优惠
  - 人工成本
  - 房租日摊
  - 水电杂费
  - 营销投流
  - 设备维修
  - 报废损耗

家庭后净现金流 =
  经营净现金流
  - 家庭固定支出
  - 贷款还款
```

### 10.3 可撑天数

```text
最近现金流缺口 = max(最近 7 天平均家庭后净现金流的绝对值, 最低日固定成本)
可撑天数 = 当前现金 / 最近现金流缺口
```

边界处理：

- 如果最近家庭后净现金流为正，可撑天数显示为 `稳定`，但仍展示固定成本压力。
- 如果当前现金小于 0，进入债务风险判断。
- 如果债务和家庭压力同时过高，允许触发“返贫触发”结局。

### 10.4 结局判断

优先级从高到低：

| 结局 | 触发条件示例 |
| --- | --- |
| 返贫触发 | 现金为负、债务超过阈值、家庭压力爆表 |
| 家庭透支 | 店铺未关，但家庭压力长期高于 85 |
| 借债续命 | 债务增长明显，现金流仍为负 |
| 虚假繁荣 | 总流水高，但累计净现金流为负 |
| 谨慎止损 | 主动转让且家庭现金流未击穿 |
| 微利跑通 | 连续多个周期家庭后净现金流为正 |
| 稳健转型 | 早期退出或转向轻资产方案 |

## 12. MVP 开发计划

### 12.1 第一阶段：项目骨架和快速体验版

前端：

- 初始化 Vite React AntD 项目。
- 完成首页、角色选择、赛道选择、经营台、账本页、报告页。
- 完成 API 封装和当前局 store。

后端：

- 初始化 FastAPI 项目。
- 建立 MySQL 连接、SQLAlchemy 模型和 Alembic 迁移。
- 实现内容 seed 导入。
- 实现创建游戏局、查询游戏局、提交决策结算、查询账本、生成报告接口。

数据库：

- 创建配置表和运行表。
- 导入第一批角色、赛道、事件卡、决策卡、结局规则。

验收：

- 用户可以完成 7 天快速体验版。
- 每天能提交决策并生成账本。
- 第 7 天能生成体检报告。

### 12.2 第二阶段：完整流程版骨架

前端：

- 增加章节状态机页面。
- 增加筹备开店表单和启动资金表。
- 增加危机与诱惑页面。

后端：

- 支持 phase 流转校验。
- 支持周结算。
- 支持事件条件触发和 flags。

验收：

- 用户能走完动心、评估、选赛道、筹备、开业、稳定经营、危机、结局。
- 中途刷新后可以恢复当前局。

### 12.3 第三阶段：报告和传播增强

前端：

- 完善图表和报告视觉。
- 生成分享文案和截图区域。

后端：

- 优化结局评分和报告分析。
- 增加更多事件卡和决策卡。

验收：

- 至少 30 张经营事件卡、15 张家庭/心理事件卡、20 张决策卡。
- 至少 7 种结局。
- 报告能指出最大亏损来源、危险决策和止损建议。

## 15. 风险与约束

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 规则过复杂 | 第一版如果模拟过细，会影响开发周期 | 先做核心现金流和家庭压力 |
| 内容配置不足 | 卡片少会导致重复感强 | seed 先保证 7 天体验不重复 |
| 前端状态混乱 | 章节多、指标多 | 后端作为状态源，前端只缓存当前局 |
| 账本不可信 | 用户看不懂为什么亏 | 后端返回结算拆解，前端明确展示 |
| 价值观偏差 | 题材容易变成嘲讽困境 | 文案保持现实、克制、尊重 |

## 16. 开发优先级

第一批必须完成：

1. 前后端项目骨架。
2. MySQL 表结构和 seed 数据。
3. 快速体验版完整闭环。
4. 现金流账本和可撑天数。
5. 结局报告。

第二批再做：

1. 完整流程版章节。
2. 危机与止损系统。
3. 更丰富的事件卡和图表。
4. 分享能力。

第三批再考虑：

1. 内容后台。
2. 登录和多设备存档。
3. 排行榜。
4. 真实经营测算工具衔接。
